Technical Notes สำหรับทีมไอทีลูกค้า

      ▾
    

    

    

    
ประเด็นสำคัญที่ควรทราบก่อนเริ่ม Implementation จริง


    

      

        
🔑

        
key และ token_key คืออะไร

        
key คือรหัสอ้างอิง Consent Form ที่ได้รับจาก NDPP Console ตอนสร้างฟอร์ม มีค่าคงที่ต่อฟอร์มหนึ่งใบ ส่วน token_key คือโทเคนที่สร้างขึ้นเฉพาะแต่ละรายการ/ผู้ใช้งาน ใช้ยืนยันตัวตนของ transaction นั้นๆ ไม่ควรใช้ซ้ำข้ามรายการ

      

      

        
⚠

        
ห้าม Cache Purpose ฝั่ง Client

        
ต้องเรียก API 3.1 ใหม่ทุกครั้งที่เปิดฟอร์ม ห้ามเก็บ purpose_options ไว้ใช้ซ้ำเกินอายุ session เนื่องจากแอดมิน NDPP อาจแก้ไขรายการ Purpose ได้ตลอดเวลา การ cache อาจทำให้ลูกค้าเห็นข้อมูลที่ไม่เป็นปัจจุบัน

      

      

        
⚡

        
Error Handling / Edge Cases

        
ควรสอบถามทีม NDPP เรื่อง retry policy เมื่อ API ตอบกลับช้าหรือ timeout, พฤติกรรมเมื่อ key/token_key หมดอายุหรือไม่ถูกต้อง, และควรออกแบบ fallback UI ไว้รองรับกรณีเรียก API ไม่สำเร็จ

      

      

        
🔒

        
ความปลอดภัยของการเชื่อมต่อ

        
การเรียก API ทั้งหมดต้องผ่าน HTTPS เท่านั้น ไม่ควรฝัง key/token ไว้ใน client-side ที่มองเห็นได้ง่ายเกินจำเป็น และควร log การทำรายการไว้ฝั่ง Viriyah เพื่อสอบทานย้อนหลังร่วมกับ NDPP ได้

      

    


    

      

        
ถ้า purpose_option ที่ส่งไปไม่ครบตามที่ API 3.1 ส่งมา จะเกิดอะไรขึ้น? ▾

        
ควรยืนยันกับทีม NDPP ว่าระบบจะปฏิเสธคำขอ (reject ทั้งหมด) หรือบันทึกเฉพาะรายการที่ส่งมา — เป็นจุดที่ควรทดสอบร่วมกันก่อนขึ้นระบบจริง

      

      

        
Purpose Version ใช้ทำอะไร? ▾

        
ใช้อ้างอิงว่าลูกค้าให้ความยินยอมภายใต้เนื้อหา/เวอร์ชันของ Purpose ชุดใด เพื่อรองรับกรณีที่แอดมินแก้ไขข้อความ Purpose ในภายหลัง และต้องพิสูจน์ย้อนหลังว่าลูกค้ายินยอมกับข้อความฉบับใด

      

      

        
ต้อง implement ฝั่ง Frontend หรือ Backend ก่อน? ▾

        
แนะนำให้เรียก API 3.1 และ 3.2 ผ่าน Backend/Server-side ของ Viriyah เพื่อไม่ให้ key ถูก expose ตรงๆ บน client และสามารถควบคุม logging/error handling ได้ดีกว่า

  • 1. Fallback to Cache — กรณี API 3.1 fail ใช้ cached purpose ล่าสุด (ตาม Option A/B/C) แสดงชั่วคราว พร้อม flag "ข้อมูลอาจไม่ใช่เวอร์ชันล่าสุด"
    • 
          
  • 2. Client-side Buffer — กรณี API 3.2 fail เก็บ transaction ที่ยิงไม่สำเร็จไว้ใน buffer/queue ชั่วคราว พร้อม timestamp และ payload
    • 
          
  • 3. Retry Mechanism — ตั้ง retry policy (exponential backoff) ให้ระบบส่ง transaction ค้างซ้ำเป็นระยะจนกว่า NDPP จะกลับมาออนไลน์
    • 
          
  • 4. NDPP-side Recovery API — endpoint เฉพาะ เช่น POST /preference-consent/recover รับ original timestamp (เวลาที่ user กดจริง) เพื่อ audit trail และเช็ค duplicate ด้วย idempotency key
    • 
          
  • 5. Monitoring / Alert — แจ้งเตือนทั้งสองฝั่งเมื่อ buffer มี transaction ค้างเกินเวลาที่กำหนด เพื่อให้ทีม manual-check ได้ทัน
